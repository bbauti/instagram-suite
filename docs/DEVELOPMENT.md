# Development guide

This is the contributor how-to for **Instagram Suite** — a single paste-into-the-console
SPA bundling three tools (Ledger, Followers, Pending) over one shared core. There is no
backend and no runtime build server: you build a single JS file locally and paste it into
Chrome DevTools on `instagram.com`.

If you only want to *use* the tool, see [`README.md`](../README.md). This document is for
people editing the source.

---

## Prerequisites

- **Node.js + npm.** Only needed to run the bundler; it is not used at runtime.
- A Chromium-based browser (Chrome/Edge) with DevTools, logged into Instagram, for testing.

The project has **two devDependencies**: [`esbuild`](https://esbuild.github.io/) (the bundler)
and [`lit-html`](https://lit.dev/docs/libraries/standalone-templates/) (the UI rendering
library). lit-html is bundled into the output by esbuild, so there is nothing extra to install
at runtime.

---

## Setup

```bash
npm install
```

This installs `esbuild` and `lit-html` (the devDependencies) into `node_modules/`.

---

## Build

```bash
npm run build
```

This runs the `build` script from [`package.json`](../package.json):

```
esbuild src/main.js --bundle --format=iife --minify --charset=utf8 --legal-comments=none \
  --outfile=dist/instagram-suite.js \
  --banner:js="/* Instagram Suite — generated from src/. Do not edit this file; edit src/ then run: npm run build */"
```

It bundles the whole `src/` tree, entry point [`src/main.js`](../src/main.js), into a single
file at **`dist/instagram-suite.js`**. That built file is what you paste into the console.

### Watch mode

```bash
npm run watch
```

Same build with `--watch`: esbuild rebuilds `dist/instagram-suite.js` on every save. You
still have to re-paste the file into the console to pick up changes (there is no hot reload —
it is a pasted script).

### How the bundle is produced — and why it must stay paste-safe

The source is normal ES modules (`import`/`export` across `src/core`, `src/ui`, `src/tools`).
esbuild is invoked with:

- `--bundle` — follow every `import` and inline it into one file.
- `--format=iife` — wrap the whole thing in an Immediately Invoked Function Expression.
- `--minify` — collapse whitespace, shorten **local** identifiers, fold/drop dead code. Minify
  only renames locals: the `globalThis.IGS` / `globalThis.__igsSelfTest` handles, object keys,
  CSS classes, and the `console` self-test/warnings all survive. (Don't add `--drop:console` — it
  would gut the self-test and the off-host warning.)
- `--charset=utf8` — keep the UI's Unicode glyphs (✕ ⚠ ▲ — …) raw instead of `\uXXXX` escapes;
  smaller, and correct since the file is pasted as UTF-8.
- `--legal-comments=none` — drop bundled-dependency (lit-html) license comments from the output.

The IIFE format is the important part. The console paste target is a bare `<script>`-style
eval, **not** a module context, so any surviving `import`/`export` statement would throw
`Cannot use import statement outside a module` the moment you paste it. `--format=iife`
strips all module syntax and resolves every cross-file reference internally, leaving a
self-contained blob that runs anywhere you paste it. Keep it that way:

- Author `src/` as ES modules; let esbuild flatten them.
- Don't add anything that needs a module/`type="module"` host at runtime (top-level
  `import()` of external URLs, `import.meta` host assumptions, etc.).
- The only globals the bundle is allowed to create are the ones it already creates:
  `globalThis.IGS` and `globalThis.__igsSelfTest` (see below).

### The Golden Rule

> **Edit files under `src/`. Never edit `dist/instagram-suite.js`.**

`dist/instagram-suite.js` is generated output. Any change you make there is silently wiped
the next time anyone runs `npm run build`. The fix-loop is always: edit `src/` → `npm run
build` → re-paste `dist/instagram-suite.js`.

## Self-test

[`src/selftest.js`](../src/selftest.js) exports `selfTest()` — a tiny runnable check on the
parts most likely to break silently:

- the **diff math** (gained/lost set arithmetic via `byId`),
- the **backoff schedule** (`1,2,4,8,16`, capped at 16),
- HTML **escaping** (`esc`).

It uses `console.assert` and logs `__igsSelfTest passed` on success.

It is wired into [`src/main.js`](../src/main.js) two ways:

1. **Automatically at boot.** main runs `globalThis.__igsSelfTest()` once at the end of
   startup (wrapped in `try/catch`, so a failing assert is non-fatal and never blocks the
   overlay).
2. **On demand from the console.** main also exposes it as a global handle:

```js
globalThis.__igsSelfTest();   // re-run the check; returns true, asserts in console
```

So to run it manually: build, paste `dist/instagram-suite.js` into the DevTools console,
then call `__igsSelfTest()`. Watch the console for any failed `console.assert` lines.

If you touch diff logic, the queue backoff formula, or `esc`, add the smallest possible
assertion to `selfTest()` rather than a separate test harness — that is the project's whole
test strategy.

## Add a new tool

A tool is a plain object implementing the **tool contract**:

```
{ id, label, boot(), mount(el), unmount(), onQueueChange() }
```

- `id` — unique string, also the `mount('<id>')` key and the nav `data-mod` value.
- `label` — text shown in the top nav.
- `boot()` — called once at startup. Register your queue handlers and load persisted state
  here. Don't render.
- `mount(el)` — render your UI into the given container element (`app.view`).
- `unmount()` — called when the user switches away; clean up / persist last view.
- `onQueueChange()` — called when global queue state changes; call `update()` to re-render.

### 1. Create `src/tools/mytool.js`

Follow the existing tools (each is an IIFE that returns the contract object — see
[`src/tools/ledger.js`](../src/tools/ledger.js), [`followers.js`](../src/tools/followers.js),
[`pending.js`](../src/tools/pending.js)). Minimal skeleton:

```js
// src/tools/mytool.js
import { html, render } from 'lit-html';
import { store } from '../core/store.js';
import { queue } from '../core/queue.js';
import { api } from '../core/api.js';

export const mytool = (() => {
  const K = { state: 'igs-mytool-state' };   // localStorage keys, igs- prefixed
  let container = null;
  let st = { /* in-memory view state */ };

  // one template() for the whole view; events bound inline (@click, @input, …)
  const template = () => html`
    <div class="panel"><h2>My Tool</h2>
      <p>viewer #${api.viewerId || '—'}</p>
      <button @click=${() => { st.n = (st.n || 0) + 1; update(); }}>clicked ${st.n || 0}</button>
    </div>`;
  const update = () => render(template(), container);

  return {
    id: 'mytool',
    label: 'My Tool',
    boot() {
      // register queue handlers (if any) + load persisted state
      st = store.get(K.state, st);
    },
    mount(el) { container = el; update(); },
    unmount() { store.save(K.state, st); },
    onQueueChange() { if (container) update(); },
  };
})();
```

lit auto-escapes `${…}` text, so there is no `esc()` in templates. For a search box bind
`` .value=${live(st.query)} `` (import `live` from `lit-html/directives/live.js`) so the caret
survives re-renders, and key lists of users with `repeat(items, u => u.id, tpl)`.

### 2. Register it in `src/main.js`

Import it and add it to the `modules` list passed to `setModules`:

```js
import { mytool } from './tools/mytool.js';
// ...
const modules = [ledger, followers, pending, mytool];
setModules(modules);
modules.forEach((m) => m.boot?.());
```

That is all the shell needs: [`renderShell()`](../src/ui/shell.js) builds the nav button from
each module's `id`/`label`, and `mountModule(id)` swaps tools by calling
`unmount()`/`mount()` for you. Optionally allow `IGS.mount('mytool')` — it already works,
since `IGS.mount` is `mountModule`.

### 3. Build and test

`npm run build`, paste, and check your nav button appears and mounts.

## Add a queue action kind

The [global queue](../src/core/queue.js) is one shared, paced, rate-limit-safe engine used
by all tools. You don't write your own pacing/retry loop — you register a **handler** for a
**kind** and enqueue items.

### 1. Register a handler in your tool's `boot()`

```js
boot() {
  queue.register('mykind', {
    run: (item) => api.someAction(item.userId),       // required; async ok; return a result
    onDone: (item, res) => { /* update snapshot/UI state on success */ },
    onFail: (item, err) => { /* terminal failure after retries/404 */ },
  });
}
```

- `run(item)` is the only required method. Throwing triggers the engine's retry/backoff;
  throwing a `RateLimit` (from `core/api.js`) triggers the global ~10-minute auto-pause.
- `onDone(item, res)` receives whatever `run` returned.
- `onFail(item, err)` fires only when an item is *terminally* failed (404, or
  `MAX_RETRIES = 4` exhausted).

### 2. Enqueue items

```js
queue.enqueue([
  { kind: 'mykind', userId: u.id, username: u.username, fullName: u.fullName, isVerified: u.isVerified },
]);
```

`enqueue` de-dupes by `userId + kind`, unpauses, persists, starts the engine, and fires
`onChange`. The engine then paces them one at a time at the selected `SPEEDS` rate with a
cooldown between actions.

### 3. (Optional) give the kind a verb label

For the queue panel's status line ("Working @user…"), add an entry to `KIND_VERB` in
[`src/core/queue.js`](../src/core/queue.js):

```js
export const KIND_VERB = { /* ...existing... */ 'mykind': 'Doing' };
```

Existing registered kinds, for reference: `unfollow` (Ledger), `fm-follow` / `fm-unfollow`
(Followers), `verify` / `cancel` (Pending).

> Keep `run` idempotent-ish and tolerant: items survive a refresh (`running` → `pending` on
> reload), so an action may be attempted more than once.

## Coding conventions

Match the existing style — **do not propose rewrites**:

- **Lean style.** Smallest thing that works. Prefer one expression over five
  lines, the standard library over a helper, a native browser feature over a dependency. The UI
  rendering layer is `lit-html` (bundled in); beyond that, reach for native browser features
  before adding another dependency — e.g. the in-browser ZIP reader uses `DecompressionStream`,
  no third-party library.
- **Modern ES only.** Arrow functions, `const`/`let`, template literals, `async/await`,
  optional chaining (`?.`), `structuredClone`, `replaceAll`, `dataset`,
  `crypto.getRandomValues`. The build target is current Chrome, so use it.
- **Tidy.** No dead code, no needless complexity, no duplicated blocks.
- **Lightly commented.** A short header comment per file explaining its job; sparse inline
  notes only where intent isn't obvious.
- **Documentation lives in `docs/`,** not as comment walls in the source. If something needs
  a paragraph of explanation, it belongs here or in another `docs/` file.
- **localStorage keys are `igs-`-prefixed** and go through [`store`](../src/core/store.js)
  (`get/setRaw/save/remove`) so they get quota-safe compaction for free.
- **Rendering model.** lit-html. Each tool exposes one `template()` returning an `` html`…` ``
  template and `update = () => render(template(), container)`; bind events inline (`@click`,
  `@input`) and call `update()` on any state change — lit diffs the DOM, so search focus and
  scroll survive (no manual partial re-renders). Use `` .value=${live(st.query)} `` on search
  inputs and key user lists with `repeat(…, u => u.id, …)`. Cap rendered rows at `ROW_CAP`
  (600); search still filters the full set.

## Troubleshooting

- **Not on `instagram.com` → scans/actions disabled.** `api.loggedIn` is false off-host, so
  main logs a warning and the shell shows "⚠ not on instagram.com". Ledger/Followers can't
  hit the API, but the **Pending importer still works** — it browses entirely from your
  imported data export with zero API calls. (Verify/Cancel in Pending still need a logged-in
  session.)

- **Rate-limited → queue auto-pauses ~10 minutes.** When `run` throws a `RateLimit` (HTTP
  429, `feedback_required`, spam/checkpoint signals, or a `RATE_LIMIT_RE` match), the queue
  sets `rateLimitedUntil` for `RL_WAIT_MS` (10 min), pauses **all** tools, and auto-resumes
  when the timer elapses. The queue panel shows the countdown. This is expected; don't fight
  it. The **Fast** speed materially raises block risk — **Safe** is the default for a reason.

- **Storage full → snapshots auto-compact.** [`store.save`](../src/core/store.js) catches
  quota errors and retries with a compacted record (drops everything but `id`, `username`,
  `isVerified`, `isPrivate` from `followers`/`following`/`users` arrays, tagged `_compact`).
  If even that fails it returns `false`. The ceiling is the ~5 MB localStorage limit; very
  large accounts are the only ones expected to hit it.

- **Pasted an old build / edited `dist/`.** Remember the Golden Rule: edit `src/`, run
  `npm run build`, re-paste `dist/instagram-suite.js`. A stale dist is the most common
  "my change didn't show up" cause.

- **`import statement outside a module` on paste.** The bundle lost its IIFE wrapping —
  confirm the build ran with `--format=iife` (it does via `npm run build`) and that you
  pasted `dist/instagram-suite.js`, not a raw `src/` file.
